# Nexus Roulette

Telegram мини-апп для компьютерного клуба: клиент сканирует QR на ресепшене,
крутит рулетку и забирает приз на стойке. Владелец видит в приложении, что
выигрывают, что забирают и что сгорает.

## Как это работает

**Клиент.** Наводит камеру на наклейку с QR → открывается Telegram → сразу
открывается рулетка с уже начисленным прокрутом. Ни диктовать ID, ни ждать
сотрудника не нужно. Выигранный приз лежит во вкладке «Призы» с кодом; код
показывается сотруднику на стойке.

**Сотрудник.** Вкладка «Касса» в приложении: вводит код с телефона клиента и
видит, что выдавать и кому. Сверять глазами ничего не нужно — сервер сам решает,
годен ли код. То же самое делает бот, если прислать ему код сообщением. Может
начислить прокрут вручную по числовому ID или `@юзернейму` клиента.

**Владелец.** Вкладка «Админ» внутри приложения: отчёт с воронкой по каждому
призу, редактор призов и весов, база клиентов, персонал и настройки.

## Устройство

| Файл | Зачем |
|---|---|
| `schema.sql` | Вся база: таблицы и SQL-функции. Выполняется в Supabase |
| `api/checkin.js` | Чек-ин по QR, начисляет прокрут |
| `api/spin.js` | Прокрут рулетки |
| `api/inventory.js` | Стартовое состояние приложения |
| `api/config.js` | Сектора колеса |
| `api/qr.js` | Генерация QR-кода наклейки |
| `api/redeem.js` | Касса: погашение кода сотрудником |
| `api/webhook.js` | Бот: погашение кодов, ручное начисление |
| `api/admin.js` | Кабинет владельца: разделы через `?r=` |
| `lib/guard.js` | Проверка подписи Telegram и ролей |
| `qr.html` | Страница печати наклеек |

Критичные операции — списание прокрута, выбор приза, погашение кода — вынесены
в SQL-функции (`do_spin`, `do_checkin`, `do_redeem`). Каждая работает одной
транзакцией, поэтому двойной тап по кнопке не даёт двух призов, а два
сотрудника не могут погасить один код дважды.

## Правила выдачи

**Сгорание.** У каждого приза свой срок в днях, он отсчитывается от момента
выигрыша и дальше не меняется.

**Кап на неполученные призы.** Пока у клиента больше `max_unused_prizes`
живых непогашенных кодов, рулетка не крутится и просит забрать своё на стойке.
Прокрут при этом не тратится. Ноль в настройке снимает ограничение.

**Мгновенные призы.** Колонка `prizes.effect` задаёт, что делает приз:
`item` — обычный предмет с кодом, `respin` — сразу возвращает прокрут,
`bonus_next` — следующий чек-ин даст два прокрута вместо одного. Эффекты не
создают предмет: гасить на стойке нечего. Поле структурное и из кабинета не
правится — новые эффекты добавляются в `do_spin`.

## Настройка

### 1. База

Supabase → SQL Editor → New query → вставить `schema.sql` → Run.
Скрипт идемпотентный, повторный запуск ничего не сломает.

В строке с `insert into staff` укажите свой Telegram ID (узнать: команда `/id`
в боте) — это владелец, которому видна вкладка «Админ».

### 2. Переменные окружения в Vercel

Settings → Environment Variables:

| Имя | Значение |
|---|---|
| `BOT_TOKEN` | токен бота от BotFather |
| `WEBAPP_URL` | адрес деплоя, например `https://nexuscyberclub.vercel.app` |
| `SUPABASE_URL` | Supabase → Settings → API → Project URL |
| `SUPABASE_SERVICE_KEY` | там же, ключ `service_role` |
| `OWNER_IDS` | *(необязательно)* запасной вход в кабинет, если таблица `staff` недоступна |
| `BOT_USERNAME` | имя бота без `@` — из него строится ссылка «Включить напоминания» |
| `CRON_SECRET` | *(рекомендуется)* любая длинная случайная строка. Если задана, ежедневную задачу может запустить только планировщик Vercel |

После добавления переменных нужен передеплой — Vercel подхватывает их только
при новой сборке.

### 3. Main Mini App в BotFather — обязательный шаг

Без этого ссылка `t.me/бот?startapp=...` откроет чат с ботом, а не приложение,
и QR работать не будет.

```
/mybots → выбрать бота → Bot Settings → Configure Mini App
→ Enable Mini App → указать адрес из WEBAPP_URL
```

### 4. Вебхук бота

Один раз открыть в браузере, подставив свои значения:

```
https://api.telegram.org/bot<BOT_TOKEN>/setWebhook?url=<WEBAPP_URL>/api/webhook
```

В ответе должно быть `"ok":true`.

### 5. Наклейка

Открыть `<WEBAPP_URL>/qr` в браузере, задать метку точки и распечатать.
Метка попадает в отчёт: сделайте разные наклейки для ресепшена (`r1`), столов
(`tables`) и листовок (`flyer`) — будет видно, какая реально приводит людей.

## Проверка после деплоя

1. Отсканировать QR камерой телефона → приложение открылось, прокрут доступен
2. Крутить → колесо останавливается на секторе выигранного приза
3. Отсканировать второй раз → нового прокрута нет, показано время до следующего
4. Быстрый двойной тап по «Крутить» → списывается ровно один прокрут
5. Прислать код боту → погашен; прислать его же повторно → «уже погашен»
6. Владелец видит вкладку «Админ», обычный клиент — нет
7. Поменять вес приза в кабинете → перезайти → сектор изменил ширину

## Настройка акции

Всё в кабинете, без правок кода и деплоя:

- **Максимум неполученных призов** — тот самый кап. Чем он меньше, тем чаще
  клиент вынужден заходить за призами.

- **Вес** задаёт шанс выпадения приза. Приз выбирает сервер, лента лишь
  доезжает до его карточки — подкрутить результат с телефона нельзя.
- **Лимит в сутки** ограничивает выдачу дорогих призов — «не больше двух VIP
  в день» вместо надежды на теорию вероятностей.
- **Срок сгорания** — рычаг возврата: чем короче, тем быстрее клиент придёт,
  но тем больше призов сгорит зря. Смотрите на колонку «Сгорел» в отчёте.
- **Процент «Забрали»** — главный индикатор. Если призы выигрывают, но за ними
  не приходят, акция не работает: либо приз не нужен, либо срок слишком мал.

## Уведомления клиентам

**Напоминание о сгорании.** Раз в сутки бот сам пишет тем, у кого приз
сгорает в ближайшие часы, и добавляет к сроку немного времени — чтобы
человек успел дойти, а не махнул рукой. Расписание задаётся в
`vercel.json`, пороги — в кабинете, раздел «Связь». Одно напоминание на
приз: повтор невозможен, отметка ставится в базе тем же запросом,
которым приз выбирается.

**Массовая рассылка.** Там же, в разделе «Связь»: текст, выбор аудитории
и отправка с прогрессом. Аудитории — все, активные за 30 дней, пропавшие
больше чем на 30 дней и те, у кого на руках невыкупленный приз. Обрыв
связи не задваивает сообщения: список получателей помнит, кому уже ушло,
и отправку можно продолжить.

**Фото в рассылке.** К объявлению можно прикрепить картинку — афишу
турнира, фото акции. Приложение само ужимает снимок перед отправкой, так
что размер файла значения не имеет. Учтите одно: с картинкой Telegram
разрешает подпись до 1024 символов вместо 4096, приложение показывает
счётчик и не даст отправить лишнее.

**Почему уведомления доходят не всем.** Telegram запрещает боту писать
первым, пока человек сам не начал с ним переписку, а мини-апп, открытый
по ссылке с наклейки, такого разрешения не даёт. Обойти это ограничение
нельзя, но спросить разрешение можно в один тап: клиент открывает
вкладку «Призы» и жмёт «Включить напоминания» — Telegram показывает своё
окно прямо поверх приложения, уходить в чат не нужно.

В разделе «Связь» есть поимённый список тех, до кого бот пока дотянуться
не может, отсортированный по числу призов на руках: именно у этих людей
приз сгорит без предупреждения. Попросить их нажать кнопку можно на
стойке, а тем, у кого сохранён телефон, — позвонить.

**Кнопка меню в чате бота.** Панель под полем ввода настраивается один
раз и хранится у Telegram, поэтому вбитый туда когда-то адрес продолжает
открывать старую версию приложения даже после переезда. Кабинет → Клуб →
«Привязать к этому приложению» переписывает её на текущий адрес, соседняя
кнопка убирает совсем.

## Бронирование мест

Вкладка «Бронь». Клиент выбирает зал, день, время и длительность, видит
схему зала как в кинотеатре, тыкает свободное место, выбирает тариф и
бронирует. Занятые места показаны серым — занятость считается на сервере
именно для выбранного промежутка.

Сотрудники и владелец сразу получают сообщение от бота: зал, место,
тариф, время, длительность, сумма, имя и телефон клиента, код брони. На
вкладке «Касса» появился список броней на сегодня — **его нужно
открывать перед посадкой гостя**, иначе можно занять забронированное
место.

**Модуль демонстрационный.** Расписание живёт в нашей базе, а не в
системе управления клубом, и онлайн-оплаты нет: деньги берутся на стойке.
Это сделано намеренно — чтобы показать, как работает запись, до
договорённостей об интеграции. Kaspi или Apple Pay встраиваются ровно в
шаг подтверждения брони.

Двойная бронь невозможна на уровне базы: пересечение по времени для
одного места запрещает ограничение PostgreSQL, а не проверка в коде.
Проверка проиграла бы гонку — два одновременных запроса увидели бы место
свободным и оба записались.
